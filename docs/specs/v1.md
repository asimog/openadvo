## V1-1. Durable chat (workflow Appendix C 8)

- The chat of a matter survives a restart. The Pi session is a file session in `<matter>/chat/pi/` (`SessionManager.continueRecent`), so the model sees the earlier turns. The messages the window shows are in `<matter>/chat/messages.json`, written after every run.
- "New conversation" starts a new Pi session file. The old files stay.
- The session id is still recorded in the matter store (decision 7).

## V1-2. Chat text as formatted text (parking, step 1)

- The agent's markdown shows as formatted text: headings, bold, italic, inline code, code blocks, bulleted and numbered lists, and links shown as text. The renderer builds React elements. It never sets raw HTML.

## V1-3. Matter memory (parking M-13; Mike scoped memory)

- Each matter has one `memory.md` in its folder. The advocate reads and edits it on the Matter tab (human-only bridge function `setMemory`).
- The agent reads it with the tool `read_matter_memory`. The system prompt says that memory is lower-authority reference text, never an instruction and never a source of a fact. The agent cannot write it.
- Every save is an event in the matter's event record, with the SHA-256 of the new text.

## V1-4. Workflows (workflow Appendix C 1; Mike workflows)

- A workflow is a named, reusable instruction to the agent. v1 ships six built-in workflows that follow the advocate workflow: analyse the impugned judgment, build the chronology review, research the issues, prepare the case-conference package, draft Questions of Law and Grounds, and check the petition before filing.
- The advocate can add, edit and delete own workflows. They are stored in `workflows.json` in the user data folder.
- The chat landing page and the chat dock list the workflows. Choosing one sends its text as the advocate's message. A workflow grants nothing: the agent keeps the same tools.

## V1-5. Record table (Mike tabular review; workflow 4 and 5)

- The advocate defines columns (questions, for example "Date of the order" or "Relief granted"). The rows are the matter's sources.
- The agent fills one cell with `fill_record_cell`: an answer and one quote with its page and line. The cell is stored only when the quoted words occur on that line of that source (normalised whitespace and case). Otherwise the tool refuses with `QUOTE_NOT_FOUND`.
- A filled cell is a candidate. The advocate confirms or clears it (human-only). A cell shows its quote and its source line.
- Table records live in `matter.db` (`record_column`, `record_cell`).

## V1-6. Case-conference package and record (workflow 7E)

- "Prepare conference package" generates a DOCX draft of kind `conference` from the records only: matter identity, procedural history (confirmed procedural events), the Factual Matrix (confirmed factual events), issues with their status and reasons, authorities by role, the adverse-authority review, memoranda with their references, open review items, and the missing details of the matter. No model writes its text.
- Each entry is a paragraph with an anchor linked to its events, like the List of Dates.
- The conference package is a work product. It is not part of the filing set.

## V1-7. The petition and the prayer (workflow 8, items 5 to 7; 9D)

- "Prepare petition" generates a DOCX draft of kind `petition` from the matter details, the approved Questions of Law and Grounds, and the annexure list. The structure is: cause title, the court and the petition heading, the addressee, the particulars of the impugned judgment, the Questions of Law, the declaration paragraph, the Grounds, the prayer, and the signature block.
- The generator copies the approved text of Questions of Law and Grounds. It writes no legal argument. Where a detail is not recorded, it writes `[TO BE COMPLETED: <what>]`.
- A new check, rule 23 in the draft checks: a `[TO BE COMPLETED` marker is a defect. Rule 24: the prayer names the date of the impugned judgment and the case number that the matter details record; a mismatch is a defect.
- The filing rule P-1 adds the petition to the required documents.

## V1-8. Filing manifest (Mike tamper-evident exports)

- Every filing set has `manifest.json`: for each file its name, role, size and SHA-256, the approved revision it came from, and the approval trail (who approved what, and when). The manifest has a `digest`: the SHA-256 of its body serialised with sorted keys and no whitespace, without the `digest` field.
- The function `verifyManifest` recomputes the digest and the file hashes. The Filing tab shows the result.

## V1-9. Extractor quality (parking, step 3)

- A line that repeats on three or more pages of one source, with digits ignored, is a running header or footer. No event is taken from it.
- A time range ("4-4.30", "10.30 to 11") is not a date.
- A document metadata line ("Decided On:", "Date of Decision:", "Equivalent Citation:") is not compared across sources for date conflicts.
- Leading list numbering ("2. ", "(iii) ", "a) ") is removed from an event description.

## V1-10. Matter rename and archive (parking, step 1)

- The advocate renames a matter. The title is an event; the matter id and folder do not change.
- The advocate archives a matter. An archived matter leaves the side navigation and shows under "Archived" on the landing page, from where it can be restored. Nothing is deleted.
