## V2-1. Files other than PDF (workflow 3, client documents; 4)

- A matter accepts DOCX, plain text (`.txt`), PNG and JPEG files beside PDF. The matter store checks the first bytes of each file. Any other file is refused with its reason, as before.
- DOCX and text: the text of each paragraph is one line. A "page" is a block of 50 lines. The source detail says "pages are blocks of 50 lines, not printed pages". The reading is the text layer.
- PNG and JPEG: the image is read by the same OCR engine as a scanned PDF page, and marked "single reading, not cross-checked".
- A source that is not a PDF has no PDF view. The source detail shows its text lines.

## V2-2. Document type (workflow 4: detect document type and legal category)

- After ingestion, a rule reads the first page and proposes one type: judgment, order, first information report, charge-sheet, petition, application, affidavit, reply, notice, letter, or other. The proposal names the words that matched.
- A proposal is a candidate. The advocate confirms it or sets another type (human-only `setSourceType`). The source list shows the type and its status.
- `list_sources` gives the type and its status to the agent.

## V2-3. Same text, different files (Appendix B-B, kind 3)

- When two sources of one matter have nearly the same text (at least 90 per cent of their word sequences of five words in common, and each has 50 words or more), the matter store opens a review item "possible duplicate" that names both sources and the overlap.
- The advocate resolves it as "same document" or "different documents". Nothing is merged, hidden or deleted. Both files stay.

## V2-4. Relative dates (Appendix B-C)

- "today", "this day" and "the date hereof" take the document's header date: the first explicit date on page 1 of the source.
- "yesterday" takes the header date minus one day.
- "the next day", "the following day" and "the day after" take the last explicit date earlier in the same source, plus one day.
- Every such date is `inferred`, names its base date in the event, and needs the advocate's confirmation like any event. "thereafter" and other vague words give no date.

## V2-5. Choosing the List of Dates rows (parking, step 4)

- The List of Dates view lists the confirmed events with a tick box each. The advocate ticks the rows to keep (human-only `setListOfDatesRows`). The selection is stored in `matter.db`.
- When a selection exists, "Generate List of Dates" uses only the ticked rows, in date order. With no selection, it uses every confirmed event, as before.

## V2-6. Interim relief and condonation of delay (parking, V1-7)

- The matter details gain "interim relief sought". When it is recorded, the petition has a section "PRAYER FOR INTERIM RELIEF" with that text after the main prayer.
- When the confirmed limitation working shows a delay, "Prepare condonation application" generates a draft of kind `condonation`: the cause title, the number of days of delay from the limitation working, and `[TO BE COMPLETED: the reasons for the delay]`. The generator writes no reason.
- The filing rule P-1 requires the condonation application when the confirmed limitation working shows a delay.

## V2-7. Signed filing manifest (parking, V1-8)

- On first use, the application makes one Ed25519 key pair. The private key is stored encrypted with `safeStorage` in the user data folder. It never leaves the main process.
- Every new manifest carries `signature` (over its `digest`) and `publicKey`. `verifyManifest` checks the signature as well as the digest and the file hashes. A manifest without a signature (v1) is reported as "not signed", not as failed.

## V2-8. Memory proposals (parking, V1-3)

- The agent may propose a note for the matter memory with the tool `propose_memory_note` (text and reason). A proposal is stored as a candidate in `matter.db`. The agent still cannot write `memory.md`.
- The Matter tab lists open proposals. The advocate accepts one (its text is added to the end of `memory.md`, an event with the new SHA-256) or rejects it (human-only `decideMemoryProposal`).

## Not in v2

OCR disputes need a second engine. Court-listing duplicates (kind 2) need live portal capture. Insert-at-cursor and PDF scroll-to-anchor need editor APIs that the vendored build does not expose to us. These stay in [../parking.md](../parking.md).
