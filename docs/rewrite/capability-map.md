# Capability map and systems-design report

Status: **design report on the proposed architecture** (docs-only task, 2026-11-20). The subject is the system the [rewrite series](README.md) proposes — not the current code, whose verified behaviour is in [audit.md](audit.md). Every claim here is grounded in the plan documents: [boundaries.md](boundaries.md) (the eleven domains), [contracts.md](contracts.md) (the shapes), [system-architecture.md](system-architecture.md) (the composition), [decisions.md](decisions.md) (the nine owner answers), [phases.md](phases.md) (the build order), [rules.md](rules.md) (the enforceable rules).

The owner named fourteen capabilities. This report (1) identifies each capability's place, owner and features in the proposed design, (2) analyses the relationships with the six required questions, (3) applies the twenty systems-design principles, and (4) records the findings — including two clarifications the plan now carries explicitly.

## 1. The capability inventory

The owner's fourteen capabilities do not map one-to-one onto the eleven domains, and that is deliberate: four of them are cross-cutting concerns the plan deliberately does **not** make into record-owning modules. The mapping:

| # | Capability (owner's name) | What it is in the proposed design | Its single source of truth | Writes |
|---|---|---|---|---|
| 1 | **Matter Management** | The Matter domain: matters, clients, instructions, parties, lifecycle, assignments, related-matter links | Per-matter store, `matter.*` tables | Matter module only |
| 2 | **Proceeding Management** | The Proceedings domain: proceedings, case and diary numbers, parties of record, stages, hearings, orders, connected proceedings | Per-matter store, `proceeding.*` tables | Proceedings module only |
| 3 | **Matter Classification** | The intake service in application coordination: a content-assisted, cite-per-signal **proposer** (DQ-8). It computes nothing legally and writes nothing | None of its own — proposals only | Nothing (proposals are validated and applied by capabilities 1, 2 and 6) |
| 4 | **Document Management** | The Documents domain plus the OCR/PDF/blob infrastructure behind its ports: registration, versions, pages, anchors, processing state, derived representations | Per-matter store `document.*` tables + blobs by hash | Documents module only |
| 5 | **Evidence Management** | The Evidence domain: evidence records, provenance, integrity, authenticity, relations — the *status* of sources, never the bytes | Per-matter store, `evidence.*` tables | Evidence module only |

They write directory rows **through the Courts domain** and hold no legal record; filing submission is not an adapter capability (contracts §5) | Adapter files (data, versioned) | Only via the Courts domain |

## 2. The relationship matrix

Six questions per relationship: the responsibility's owner, the consumer, the connecting contract, the exchange, the coupling, and the duplication-of-logic-or-authority risk with its guard. "Guard" cites the plan's mechanism, not prose.

| Relationship | Owner of the responsibility | Consumer | Contract | Exchanged | Coupling | Duplication risk → guard |
|---|---|---|---|---|---|---|
| Matter → Proceedings | Proceedings owns case records; Matter owns the container | Proceedings | `matterId` scope + Matter query port | Matter existence, title, client, scope token | Proceedings read Matter; Matter never imports Proceedings | Matter growing court/case fields again (the audited failure) → R-5: a structural test fails if a case field appears outside Proceedings |
| Courts → Proceedings | Courts owns court/case-type/stage data | Proceedings | Courts query port; typed ids | `CourtId`, `CaseTypeId`, `StageKey`, case-number shape | Proceedings validate against Courts at write time; Courts knows nothing of matters | Proceedings copying display names → typed ids only (contracts §2); free text is a defect (rules 14) |

## 3. Notable relationships, in prose

**The record spine (Matter → Proceedings → Courts).** Proceedings owns what the old system put on a one-row profile (audit 4.5): each proceeding carries its own typed court, case type, case number and diary number. The contract is a scope plus typed ids; the coupling is one-directional and validated at write time; the duplication risk is the exact collapse the audit found, so the guard is a structural test, not a convention. Courts serves every court-specific value as sourced data with a freshness check (decision 16 kept) — adapters feed it, and no adapter is a second authority because submission is structurally absent from the adapter contract.

**The proof chain (Documents → Evidence → Facts).** Three owners in a line: bytes and anchors (Documents), evidential status (Evidence), statements and their acceptance (Facts). Each hand-off is a typed reference resolved by the receiving side's owner (R-6), so no layer re-derives what another layer owns. The deliberate subtlety: a fact may cite an anchor directly, or through an evidence record, or from an instruction, or from a proceeding event — four origins, one rule: the reference is typed, and the target's owner validates it. Evidence is never a mandatory intermediary, because instructions and judicial findings are facts without being evidence records.

**Classification is a proposer, never an authority.** DQ-8 made it content-assisted with citations, which increased its value and its risk together; the design keeps the risk closed by making its output a *proposal* that fails at apply time unless every field is a typed id and every signal cites a real anchor. The audited failure (a display-name court the next layer rejects, parties and basis produced and consumed by nothing) cannot recur as authority — it can only recur as a rejected proposal.

**Permissions as the single choke point.** Every capability, surface and tool resolves through one catalog; enforcement happens in application coordination before any operation runs. The design accepts this bottleneck deliberately: it is compile-time assembled, its lookups are constant-time, and the alternative — per-interface checks — is the audited ten-allowlist drift (F-9). The one authority split that matters: declarations fix access classes (human-only is not configurable), while the policy file only adds ask/deny on top and can never loosen them.

**The agent seam, and the relationships that must not exist.** The engine implements one interface; tools are derived from the catalog; the system prompt and every legal text are OpenAdvo's. The absent relationships are load-bearing: no agent → submission (DQ-6), no adapter → submit, no interface → store, no chat → legal record. Each absence is a coherence or structural test, because the audit showed that prose-enforced absence drifts (failures.md pattern 2).

**Two checkpointers, two kinds of recovery (DQ-4).** The workflow engine's run states and the foundation's chain are the *legal* record of work: the reconciler restarts from the last completed step, and an operation that already committed is detected by its records. The agent's checkpointer resumes only a *turn*. The two never read each other's formats — the audit found what happens when one store's mechanism quietly becomes everyone's dependency (F-17).

## 4. The twenty principles, evaluated honestly

| Principle | Materially affects this design? | Where, and what it decided |
|---|---|---|
| System boundaries | **Yes — the core decision.** | The eleven domains and the five kinds of code (boundaries §1); every audited failure was a boundary that existed only in prose |
| Domain-driven design | **Yes.** | Ubiquitous terms (matter, proceeding, fact) become records with owners; SLP and practice areas are configuration, never structure (R-5) |
| High cohesion, low coupling | **Yes.** | One writer module per table; cross-domain reads via ports; the matrix above shows every coupling is one-directional |
| Information hiding | **Yes.** | Domains expose operations and query ports, not tables; the renderer imports no domain at all (repo-structure §3) |
| Single source of truth | **Yes — the audit's headline fix.** | One owner per record (matrix), one catalog, one contract source (`gen-contracts.ts`), one chain mechanism |
| Explicit contracts | **Yes.** | The `*.schema.ts` sources; generated copies; typed result envelopes; coherence tests (R-13) |
| Dependency direction | **Yes.** | Interfaces → application → domains → foundation, infrastructure behind ports; tested per build (R-15) |
| Feedback loops | **Yes, three deliberate ones.** | The review queue (human feedback), the structural suite (drift feedback — absent in the current system), the freshness checks (intel feedback; stale never shows "passed") |
| State machines | **Yes.** | Fact statuses, document processing states, filing-set states, workflow run states — each named and tested; the assignment's "no boolean acceptance" is a state machine with a decision record |
| Data flow and provenance | **Yes — the product's spine.** | Anchor → evidence hash → fact origin → chain event; every derived artefact labelled; originals preserved (audit 6.3 kept) |
| Idempotency | **Yes, where it is owed.** | Blob write-once by hash; re-import re-registers; workflow resume detects committed operations by their records (validation revision 3) |
| Temporal modelling | **Yes.** | Dated rules with in-force checks; supersedes links instead of overwrites; `decidedAt`, `recordedAt`, chain sequence; limitation computed over dates, never stored as a bare number |
| Bottleneck analysis | **Materially, twice.** | The capability catalog and the application layer are deliberate choke points — assembled once, constant-time, tested; the audited alternative was diffusion. The per-matter store keeps one advocate's work off a shared database |
| Failure propagation | **Yes — fail closed everywhere.** | Unreadable policy denies (R-10); a failed step obeys `onFailure`; a refused gate stops the run; an operation that fails rolls back its transaction and appends nothing but a refusal |
| Observability | **Partially — a carried gap.** | The chain (legal truth), the execution trace (runs), and the review queue (pending human work) are the surfaces; there is no metrics/telemetry story, which is acceptable for a local single-user product and is recorded as a limitation if multi-advocate ever arrives |
| Least privilege | **Yes.** | Per-session tool lists are derived subsets (R-9); the agent cannot name human-only operations; scope tokens confine every operation to one matter (R-12) |
| Human-in-the-loop | **Yes — the authority model.** | The `human-only` class; approvals as review items; the two hash-bound confirmations; acceptance as a decision record (DQ-1, DQ-6) |
| Offline-first | **Yes.** | Local stores, local engine, adapters with manual-upload retrieval modes, optional LangSmith off by default; no cloud dependency anywhere in the plan |
| Evolutionary architecture | **Yes.** | The seams are the evolution points: the `AgentExecution` interface (engine swappable), adapters as data (courts swappable), pack templates (proceeding types swappable), generated contracts (surfaces swappable) |
| Reversibility | **Yes.** | Nothing is deleted — records are superseded or archived; decisions are dated and answerable (decisions.md); the engine has a working fallback (Pi); matter folders stay portable; the one-way door actually taken (no migration, DQ-3) was chosen knowingly |

## 5. Findings

Five findings, none of which overturns the plan; each is now recorded where it belongs.

1. **"Procedural intelligence" must never become a module.** The capability is real, but its parts have owners: rules data in Courts, records in Proceedings, deadlines in Work, checks in Filing. The current system's `court-intel.ts` driving three stores at once (audit 4.7) is the cautionary example. Guard: each computation is a pure function owned where its data lives, and a future "intelligence service" that reads everything would fail the import-boundary test. This is already implied by boundaries §3 rows 4 and 11; recorded here explicitly.
2. **Classification has an ordering dependency.** DQ-8 made the classifier a consumer of extracted text, so intake is a small state machine: matter created → documents extracting → proposal ready → applied. Phase 5's one-page spec (written when phase 5 starts, lesson L1) must specify that state machine and its honest on-screen states (L2).
3. **Facts have four source kinds and one rule.** Direct anchors, evidence records, instructions, proceeding events — all legal fact origins, all one mechanism: typed references resolved by the target's owner. The two-path case (anchor directly vs via evidence) is not duplication: the anchor is provenance, the evidence record is status. Recorded so no future phase "normalizes" facts through evidence by force.
4. **The policy file tightens; it never loosens.** Access classes are fixed in catalog declarations; `human-only` is not configurable. The fail-closed test gains this assertion: a policy that tries to loosen a fixed class is ignored, visibly.
5. **Observability is a carried, named gap.** Legal truth (chain), execution history (trace) and pending human work (review queue) are observable; system health is not, beyond honest processing states. Acceptable for a local single-user application; it becomes a real requirement the day DQ-2's deferred multi-advocate arrives, and it is recorded as such in [assessment.md](assessment.md).

## 6. What this report does not do

It does not change the boundary map, the contracts, the phases or the rules: every guard named above either cites an existing rule or is recorded as a phase-spec obligation under lesson L1. It does not reopen any answered decision. And it does not touch code — nothing in the rewrite series has code yet; the first structural test of these relationships runs when phase 1 starts.
