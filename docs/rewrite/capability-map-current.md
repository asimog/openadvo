# Systems design report — the current code

Status: **a standalone design report on the implemented system**, written from the code at commit `26ac806` (2026-11-20; `src/` is unchanged since). Every claim cites a file and line. The subject is what the code does today: the features that exist, who owns each responsibility, what connects them, and which design principles the implementation materially honours or misses. It evaluates; it does not propose.

## 1. The capability inventory — what is implemented

### 1. Matter Management

Implemented: matter folders with one `matter.db` each (`src/lib/matter-store/index.ts:4`; store construction only at `src/main/matters.ts:54,70`); a one-row `matter` record (`index.ts:59-64`); clients in the contacts library (`src/lib/contacts/index.ts:57`); parties and assignments-as-parties in `practice.ts` (`party` table, `practice.ts:10-91`); filing details on `matter_details` (`work.ts:35-49`: case number, CNR, impugned event, certified-copy dates, interim relief); a one-row `matter_profile` (`practice.ts:34-50`); related matters (`related_matter`, `practice.ts`); archive as a marker file, not a column (`index.ts:291-292`); matter creation orchestrated inside the entry point — `createMatterFromFields` creates the matter, writes details, profile, contact, party, and infers a hearing row (`src/main/index.ts:160-183`); agent-proposed matters kept in `matter-proposals.json` (`src/main/matter-proposals.ts:47`); export to ZIP (bridge `matters:export`, `bridge.ts:187-193`).

**Ownership:** split five ways — the store library holds the records; `matters.ts` constructs; `index.ts:160-183` composes creation; `bridge.ts` exposes ~7 handlers; the renderer holds the matters list and refresh orchestration (`App.tsx:157,207-215`). No single named owner of "create a matter".

### 2. Proceeding Management

Implemented as attributes, not records. A matter's proceeding is one TEXT field on the one-row profile (`practice.ts:40`); the filing target is one row (`filing_target`, `filing-checks.ts:11-18`); case number and CNR are free TEXT (`work.ts:39-40`); the diary number exists only inside the `filing.reconciled` event's JSON (`portal.ts:238`); hearings are records (`hearing`, `practice.ts:10-91`, reminders and policy beside them); procedural history is the Notebook event stream (`notebook_event` with the system's only anchor foreign key, `index.ts:169`). Adapter "proceedings" live per adapter version in `intel.db` (`intel-store/packs.ts:68-77`). One matter holds exactly one proceeding; the SLP proceeding is privileged in ten code paths (default pack `packs/slp.json:7` + fallback `lib/packs/index.ts:221-222`; the generic `petition` draft renders SLP text `drafts.ts:436-455`; the SLP prayer check `drafts.ts:894-897`; impugned-judgment compliance `lib/filing/index.ts:87-88`; classifier, stage, template and prompt branches — `classification/index.ts:48`, `lib/stages/index.ts:95`, `drafting/documents.ts:544`, `agent.ts:390,394`).

**Ownership:** distributed across the profile row, the details row, the adapter packs and the SLP code paths. No proceeding record exists to own.

### 3. Matter Classification

Implemented: a title-and-filenames classifier (`src/lib/classification/index.ts:27` — title, source names, profile proceeding, profile court; document content is never read); practice-area and case-type chains, first regex wins (`index.ts:32-55`); an SLP branch (`index.ts:48`); display-name courts ("Supreme Court of India", `index.ts:62`); a proposal with six fields (`index.ts:10-19`); an apply handler that consumes five fields and drops `parties` and `basis` (`bridge.ts:1013-1027`); agent chat proposals as a separate path (`matter-proposals.ts`, added at `index.ts:924`).

**Ownership:** the classifier proposes; the bridge decides what to keep; nothing validates the proposal (the apply path accepts a display-name court the filing layer later rejects — `index.ts:933-934` requires a directory id).

### 4. Document Management

Implemented: source rows with status `ok|missing|changed` (`index.ts:65-74`); append-only origins (`index.ts:75-83`); content-addressed blobs with re-hash on every read (`index.ts:596-613`); write-once anchors with geometry and text, created only by ingest (`index.ts:1132-1133,155-156`); ingest jobs and page quality (`ingest_job`, `page_quality`); duplicate pairs (`work.ts` `duplicate_pair`); document types as `source_type` rows with trigger firing (`bridge.ts:164-165`); PDF operations that each write a new source (`src/main/document-ops.ts:130`); two OCR engines (Tesseract; PP-OCR via ONNX, `lib/document-intelligence/ppocr.ts:253`) with quality metrics (`lib/document-intelligence/quality.ts:151`); integrity checking that marks but never deletes (`index.ts:718-735`).

**Ownership:** the strongest capability in the system — one store module owns registration, bytes, pages and anchors; the entry point, bridge and renderer all reach it through `Matters`.

### 5. Evidence Management

**Ownership:** the store module owns the records. Anchor integrity is enforced for Notebook events only (`index.ts:169`); every other anchor id is free TEXT inserted verbatim (`evidence.ts:40,347-348`; `work.ts:204`).

## 3. The load-bearing relationships in prose

**The entry point is the composition layer and the business layer at once.** `index.ts` wires thirty services, implements the agent's host inline, creates matters with business rules, selects filing packs, polls reminders and writes the Firm Agent's usage file (`index.ts:91-123,160-183,572-581,731-778,862-869,936-1006`). Every other module depends on what it exports. There is no seam between "what exists" and "what it does" — the relationship every other relationship passes through.

**The proof chain is the system's best work with one broken link.** Registration → origins → blobs → re-hash → anchors → evidence-with-hash-copy → facts-with-actors → chained events is a coherent provenance design, enforced by triggers, and tested (the audit found it sound). The broken link is anchor integrity outside `notebook_event`: a fact, a document part, a record cell or a memory note can cite an anchor that does not exist, and only the Notebook table enforces the reference (`index.ts:169`). The inspector validates anchor *shape* by regex (`audit.ts:128`) — the check looks right and proves nothing about existence.

**Proceeding is a string with ten interpreters.** One TEXT field is read by the drafting layer (as SLP unless told otherwise), the pack selector (as a key, with the SLP pack as the data-level default, `packs/slp.json:7`), the stage list (by regex, `lib/stages/index.ts:95`), the classifier (by regex, `classification/index.ts:48`), the filing target (one row), and the prompt ("the SLP pack for a special leave petition", `agent.ts:394`). Each interpreter re-derives the concept from text; none can ask a record.

**Permissions are a good engine bolted to ten fuel lines.** The policy engine itself — fixed denials the file cannot loosen, the party rule, the one-at-a-time ask queue, the ten-minute fail-closed timeout — is well built and well tested. Around it, ten allowlists drift with nothing watching, and the file layer fails open where the hook layer fails closed (`tool-policy.ts:130-136` against `:270-276`) — two answers to one question, in one file, both documented as "fail closed" by the header comment (`tool-policy.ts:9`).

**Human authority is real in the stores and unverified at the door.** `decideFact`, `supersedeFact`, filing confirmations and approvals throw `HUMAN_ONLY` for non-advocate actors, asserted across fifteen test files. The actor is a string the caller supplies; the bridge sets `advocate` for everything from the window (`bridge.ts:720-737`). The design works for the threat model it never wrote down; nothing would notice if a future caller lied.

**Court data has a clean seam and a leaky neighbourhood.** The adapter framework — data files, a hosts whitelist, tolerant quote matching, capability-shaped lists — is genuinely well separated. Around it, twelve code paths name specific courts (section 1.14), including the compliance row that names the Supreme Court registry for *every* court (`lib/filing/index.ts:112-118`). The seam exists; half the traffic goes around it.

**Recovery is chat-shaped only.** The one recovery path that works is the Pi session file (conversations resume, `agent.ts:2671-2736`), plus skill-run resume and helper interruption marking. Workflows cannot resume (`workflow-runs.ts:54,65,79-82`); crashed runs never reconcile; usage is lost; traces are best-effort. The system records work without owning its recovery.

## 5. Assessment

**What the current code gets right, materially.** The store layer is a real domain layer: encapsulated SQLite, append-only triggers, hash chains, re-hashed blobs, human-only methods, and behaviour tests that assert them (419 passing). Document management and the filing confirmation gate are the two strongest capabilities. Adapter-as-data is a clean evolution seam. The permission engine, where it decides, is fail-closed and well tested. The renderer holds no data access. The audit found all of these first because they are real, not because the docs say so.

**What materially fails, in order of consequence.** First, composition has no owner — the entry point, the bridge and the runtime file absorb every change (the churn data is the measurement). Second, the product's central concept has no record — a proceeding is a string with ten interpreters, and SLP occupies the generic names. Third, the enforcement mechanism for every stated boundary is prose — verified by the three-copy contract, the ten allowlists, the false single-caller claim, and a green suite throughout. Fourth, integrity is optional at one provenance link (anchors) and one authority link (the actor string). Fifth, recovery exists only for chat. Sixth, the policy answers the fail-closed question twice, differently, in one file.

**The one-line systems diagnosis.** The current implementation is a well-tested store layer wearing an unowned application — every capability that ends at a store is in good shape, and every capability that crosses the wiring layer (composition, contracts, permissions, proceedings, external state, recovery) has drifted from its own documentation while the suite stayed green. That is a boundary problem, not a size problem: the same responsibilities in smaller files would keep every failure in this report.
